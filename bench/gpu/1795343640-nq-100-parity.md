Criterion: **Q2** (quality), as a 0.6B lower bound; **I1** (the `serve/` fixture) for the CPU
comparison. Grade: `measured` for the PPL and window rows, which resolve to the committed logs in
`bench/gpu/1795343640-nq-100-parity-logs/` and `scan_summary.py`; `measured` for the CPU/PyTorch
comparison behind `ppl_q8_2k.log`; `model` for the paper-tail inference. Host: vast.ai instance
61176577, RTX 4090, 32 vCPUs, torch 2.6.0+cu124, transformers 4.51.3, `Qwen/Qwen3-0.6B-Base`. The
result does not close Q2: the product is 7B.

§2 is the measurement that ours serves the same pack, which is the part this repository adds.

The per-window CPU and PyTorch nll agree to ≤0.01 nats on all eight windows tested, including the
window where both models are catastrophically wrong. A Python read of `pack.nqp` (an independent
implementation of the format) and the Rust reader agree to the same precision. The earlier 2021
was an eight-window sample that hit one catastrophic window; the full 146-window mean is the
comparable metric.

## 3. Why the 16k sample read 2021

Two to three windows of 146 are catastrophic for every compressed model here, so an eight-window
sample is a lottery over them:

| model | windows > 8 nats | their nll | all-window PPL | tail-free PPL |
|---|---:|---|---:|---:|
| reference 1.00 | 3 (6, 10, 139) | 18.48, 19.13, 19.53 | 38.75 | 28.06 |
| ours 1.00 | 2 (0, 6) | 20.70, 20.84 | 35.55 | 28.00 |
| reference 0.80 | 2 (79, 143) | 21.95, 20.90 | 44.91 | 35.16 |
| ours 0.80 | 2 (1, 87) | 13.20, 20.12 | 40.72 | 34.02 |

**The tail tracks the first token.** Prepending BOS to the reference's three tail windows takes them
to 3.51 / 3.20 / 2.41; prepending 1024 tokens of real context takes them to 3.32 / 3.07 / 2.26. A
three-window extrapolation from that puts the reference's full-stream 38.75 at ≈27.9, near the
paper's 27.56, but the protocol has not been run on the other 143 windows, so it labels the paper's
number; it does not replace the measured row.

The mechanism, probed one token at a time through both folds: at position 0 the base model carries a
massive activation on channel 35 at layer 2 (≈6.8e3). Ours reproduces it for 144 of 146 window
starts (median ratio to base 0.93), and misses it for exactly the two catastrophic starts (`ĊĊ`,
`Ġ)`, ratios 0.0006 and 0.0010), where the residual instead grows a channel-13 outlier of norm
18.7e3 and a layer-27 outlier whose head output is a fixed token. All 128 calibration starts are
healthy (ratio ≥ 0.99 pre-KD), so these starts are absent from the fit's calibration stream:
exposure is the measured pattern. It is not a dichotomy. The base model reproduces the attractor
with no calibration at all, and `v_proj` carries the largest per-linear error (0.49 input-weighted
at layer 0), so a fit that destabilised the position-0 attractor on unseen starts would produce the
same symptom. Both readings point at sequence-start coverage as the lever, and neither is
distinguished by the probes above.

Serving openers are healthy (`<|im_start|>` gives 6394, base-like), so a turn that starts there is
not cold. A raw completion, a newline-prefixed prompt or a chunk boundary can still start cold; that
is untested.

## 6. What remains

The 7B product pack (`bench/notes/2026-11-22-handoff.md` has the inputs, the preflight and the
budget), and the tail as a quality lever: removing it is worth 1.27× at 1.00 and 1.20× at 0.80
(40.72 / 34.02 = 1.197×), more than any rank reallocation at these rates. The tail is the
first-token state of §3, so the lever is sequence-start coverage in the fit and KD, not the rate. The
unedited independent-window stream above stays the primary row. The BOS/context protocol is a
diagnostic of the first token and has run on 3 windows, all reference; running it on ours 1.00
(`0, 6`) and ours 0.80 (`1, 87`) across all 146 is the next measurement, not an assumption.
