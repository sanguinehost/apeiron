# nq: one column-code read per block of factor rows

Criterion: **T2** (turn latency), not advanced: the turn wall did not separate beyond the first
series, `phase_split --target ffn` exits 1 on this tree, and the 1,827 projection leaf is not the
turn's dominant term. The result is a projection-leaf result. Grades: `measured` for the phase times,
walls and rates; `tested` for the pooled/per-column bit equality and the mutation; `model` for the
byte traffic the nesting removes. No 7B, no 20 tok/s, no decode claim. The projection-time reduction
holds over eleven pairs; the wall reduction holds only in the first series and is stated as such.

Model: `skeleton-q8head.gguf` + `nq06-v3.nqp` (0.977441 b/w, 196 linears, 418,381,824 sign
terms/token, 28 layers, 229,376 B/position KV). Machine: i5-10210U, 4 threads, `powersave`.
`APEIRON_THREADS=4`, every run under `~/Workspace/tools/agent-guard`.

## What changed

`NqLinear::project_pooled` walks the factor rows of one stage in blocks of `R` and folds each block
against one read of the column's Q8 code and shift planes: the code load, the shift load, the digit
select and the constants are shared by every row in the block, and the 32-term block loop stays
innermost. The per-row epilogues, the `mul_q32` scales and the output-row sums keep their order, so
every output word is unchanged. `R` is `APEIRON_NQ_BLOCK` parsed once in a `OnceLock`; `0` keeps the
per-row order, absent or malformed takes `NQ_BLOCK = 4`, values clamp to `NQ_BLOCK_MAX = 8`. The
switch selects loop nesting only: the pack format, the reader choice and the public API are
untouched.

The exact and ternary readers fall back to the per-row entry, which is the same arithmetic in the
same order; only the Q8 reader is blocked. The blocked AVX2 body `code_select_block_avx2::<R>` has
the safe twin `code_select_rows_twin`, the per-row selection its vector body implements, and
`the_blocked_code_source_equals_the_per_row_source` checks the two equal over `len` ∈ {1, 7, 31, 32,
33, 63, 64, 65, 127, 128, 129, 1000, 1023} and two exponent ranges.

| llama.cpp | what it does | adopted |
|---|---|---|
| `ggml-cpu.c:1202-1203`, `:1211-1251` | 16×16 outer tile, K loop inside the tile | the nesting: a row block against one activation read, block loop innermost; `R = 4`, not 16 |
| `repack.cpp:1788`, `:1808-1812` | 4 accumulator rows × 8 columns, K inside | one vector accumulator per factor row, K inside |
| `arch/x86/repack.cpp:1113`, `:1192` | `__m256 acc_rows[16]`, LHS rows in groups of four | `R` accumulators; four rows is what fits with the five constants and stays off the spill path |
| `repack.cpp:2442` | 16×1 kernel | the narrow-shape case is the same loop with `R` rows |
| `repack.h:23-25` | 8-block-interleaved pack layout | **not** adopted: the pack is unchanged, so the code plane is read at its stored stride |

## The dominant term

Cold prefill split on the block-0 arm: `ffn` **42.3%** (25,194.0 of 58,932.7 ms), `attn.proj_in`
20.2%, `attn.core` 25.8%, `attn.proj_out` 8.8%, `norm` 0.8%, `residual` 0.7%. The projections are
71.3% of the token and `ffn` is the largest leaf; a `ffn`-only change is bounded by
1/(1 − 0.423) = **1.73×**. The measured wall ratio 1.107 sits under that bound, and the decomposition
closes: 0.713/1.145 + 0.287 = 0.910, against 1/1.107 = 0.903. Post-change (pair 4, block 4) `ffn` is
40.9% and the projections 68.6%.

`phase_split --target ffn` on the unmodified arm exits 1: it measures **decode**, where `attn.core`
owns 54.5% (ceiling 2.20×) and `ffn` 15.4% (ceiling 1.18×). That refusal is correct for a decode
claim and does not apply here; this change's claim is the prefill split above, and decode is
unchanged inside noise (`ffn` 13.356 ms/token at block 0, 13.604 at block 4).

## Byte traffic the nesting removes (`model`)

Per 32-term block the Q8 reader loads one code plane and one shift vector. Per row that is
`len/32` × 2 loads; per block of `R` rows the same loads serve `R` rows, so the code/shift traffic
falls by `R` = 4 while the weight words, the activation words and the output traffic are unchanged.
At 1,827 the cold pass reads 700 × 32 = 22,400 code planes either way; the saving is the repeat per
row, not a new tensor.

## The same change on the box (`measured`, box only)

Eight vCPU EPYC Milan, 256 MiB L3, eight threads, the same source and pack, two alternating pairs at
1,827 + 16:

| block | projection ms | median | G/s |
|---|---|---:|---:|
| 0 | 14,448.3, 14,569.7 | 14,509.0 | **53.14** |
| 4 | 13,726.9, 13,582.9 | 13,654.9 | **56.47** |

Paired ratios 1.053 and 1.073, mean **1.063** against the laptop's 1.081 over eleven pairs. The
mechanism is instruction count, not cache capacity: the nest hoists two plane loads and the eight
loop constants out of `R` rows, and a column's code plane (`in` bytes of codes plus `in/32` shift
vectors, at most ~6 KB) is L1-sized on both hosts (`model`: no cache-miss counter was read), so the
box cannot lose the effect to L3. The
0.063-to-0.081 difference is inside the laptop series' 0.949–1.365 pair range. A box ratio is
`model` for the laptop; the 1,827 laptop pairs remain the claim.

## What remains

- **1.21× short of 30 G/s** at 1,827: 24.76 G/s in the first series. The 229 window reaches
  33.60 G/s, so the 1,827 gap is KV streaming and issue headroom, not the row nest. The nest's
  mechanism is the hoist of two plane loads and eight constants per 32-term block per row; the
  inner loop still spends ~8 vector ops on each row-block, and that count, not the pack layout,
  is the next question.
- **Block 8 leads on the box.** The laptop has one unpaired block-8 run, 45.009 s, inside block
  4's 43.752–47.547 s range; the box, two alternating pairs at the same shape, separates them:

  | pair | block 4 projection ms | block 8 projection ms | ratio | wall ratio |
  |---|---:|---:|---:|---:|
  | 1 (8 first) | 13,505.9 | 12,938.4 | 1.044 | 1.029 |
  | 2 (4 first) | 13,581.3 | 12,809.5 | 1.060 | 1.042 |

  Block 8 ran last in pair 2 at the window's highest load (5.44) and still won, so the order
  control holds. This is `measured` on the box and `model` for the laptop; two laptop pairs decide
  the default, which stays 4 until they clear ~1.02 in the same direction.
- **The pack layout is not the lever.** `U` is already 1 bit/term dense: one `u32` per 32 terms,
  and a row's words run 128–352 B contiguously (the pack's `in` is 1024, 2048 or 2816), so every
  cache line is fully used and llama's `repack.h` 8-block interleave solves a 34-byte `Q8_0` block
  alignment problem this plane does not have. The register budget at block 8 is 13 of 16 YMM
  registers, so 8 is admissible on that count.
- The 0.6B fixture only. The 7B pack, the Vulkan path and the 20 tok/s product claim are untouched.
- No claim about rustc/LLVM code generation, the kernel ABI or the `unsafe` container; the blocked
  body's twin is `code_select_rows_twin`, tested equal and not a `--start-from` root, so no
  refinement theorem; `proof/regen.sh --check` has not run since the change (no Aeneas on either
  host).
- The 1,827 window is prefill with 16 decode steps; its wall ratio is not a decode ratio, and the
  decode split is attention-bound.

## Review

Reviewed by `agy` with `gemini-4-hydrogen-high` on the combined tree. It refused: the T2 header on
a leaf-only result; the L1-residency sentence as unmeasured; the missing `--opaque`/twin
registration; the absence of a quiet-window confirmation; and the duplicated selector body. This
revision adopts the first three: the criterion is "not advanced", the cache sentence is `model`, the
three AVX2 bodies and two process flags are in `SERVING_OPAQUE` with the twin debt recorded in
`proof/README.md`. The quiet-window conflict is answered by the box screen and the two-laptop-pair
condition above, not by claiming the loaded windows were quiet. The duplicated body stays as debt:
`code_select_avx2` is the per-row oracle the pooled path is checked against, and folding it into
`code_select_block_avx2::<1>` is the next change on this path, not this one.
