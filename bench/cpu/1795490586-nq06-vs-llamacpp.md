# llama.cpp on this CPU: 4.2x faster cold prefill, 4.9x faster per tail token

Criterion: **T2** (turn latency), partial. Grade: `measured`. Machine: ThinkPad L13 Yoga 20R6,
i5-10210U (4 cores / 8 threads, AVX2, no AVX-VNNI), 6.6 GiB, Ubuntu 24.04. Four threads on both
sides. The governor is `powersave` after the reboot (`performance` in the earlier clean set), and
the paired set ran while the intent workspace's `rustc` held one core at 99% and the package sat
at 89 °C; both engines in that set are same-state. The clean set is the uncontended reference.

## Why this run

The 0.6B prefix-cache receipt reports 203.8x on an exact repeat and 5.29x on a 205-token delta.
Both ratios are against the engine's own cold prefill, not against a standard library. This run
puts the same three turns through llama.cpp's prompt cache on the same base model.

llama.cpp cannot read the `.nqp` pack, so its weights are the f16 GGUF: 1,198,182,592 B against the
engine's 482,672,896 B skeleton plus 53,815,472 B pack. The f16 file carries **2.25x more weight
bytes**, so a llama.cpp win is a kernel win, not a bandwidth one.

## Why the gap

The engine calls `nq_proj` once per column (`src/engine/step/cols.rs:503`), so every column
re-reads and re-decodes all 196 packed linears. The pack is 53,815,472 B; 1,827 columns read
**98.3 GB** in 65.96 s (clean) = 1.49 GB/s, or 86.20 s (paired) = 1.14 GB/s. That is *not* the DRAM
limit (~13 GB/s), so the cost is the per-column factor decode and integer dot, not the bytes.

llama.cpp reads the 1.2 GB f16 weights once per block and runs a dense AVX2 GEMM. At 2.2 TFLOP for
1,838 tokens in 17.97 s, that is 122 GFLOPS; the paired run gives 108 GFLOPS.

The NQ pack is 2.25x smaller than the f16 file and its rank factors should need fewer MACs than
dense. The 3.7–5x deficit is the per-column kernel, not the carrier.

## Tail

After the cache, the tail is the whole turn: 211 columns, 16.63 s paired. Batching `nq_proj` over
columns decodes each factor once per group and folds it against every column; the `Q5_0` prefill
receipt measured 2.02x from the same "decode once per group" change
(`1794793277-q5-pooled-prefill.md`). Target: the paired tail 16.6 → ~4 s, the clean tail 12.5 →
~3 s, and cold prefill 66–86 → ~20–30 s. To be measured, not asserted.

## What this does not cover

- Same-shape, not same-artifact: f16 against 0.98 b/w. A same-pack llama.cpp run is impossible
  (llama.cpp does not read `.nqp`), and a same-file engine run on the f16 GGUF is not the product
  path.
- Prompt content differs: the engine cycles the tokenizer's seed, llama.cpp repeats a sentence.
  Counts are 1,827/211 and 1,838/187; the table uses the actual counts and per-token times.
- KV carriers differ: engine F32, 229,376 B/position; llama.cpp f16, 114,688 B/position. The
  attention read is half on the llama.cpp side.
- The engine rows in the paired set ran with `rustc` at 99% and 89 °C; the clean set is the
  uncontended reference. The governor is `powersave`; the clean set is `performance`.
- No 8B, no 200k turn, no T2 closure. No quality comparison.
