# `Q4_K` in the shared pooled loop: correct, and 5.8–9.6× slower than the entry it would replace

Criterion: **T2** (turn latency), through the one-path rule in `AGENTS.md`. Grade: **measured** for
the table; the equality is `tested`. Machine: i5-10210U, 4 cores / 8 threads, 15 W, 6.6 GiB,
Ubuntu 24.04, `performance`, rustc 1.99.0-nightly; the session's pool reports 2 CPUs. This receipt
does not claim T1 (decode), which is `k = 1` and does not take this route.

## What landed

`matmat_q8act`'s pooled loop now has a `Family::Q4_K` carrier: `pooled` builds the per-32-lane
`Σ xq` vector with `chart::block_xsums`, `pooled_rows` calls `chart::q4_k_row_kcols_avx2`, and
`fast_family` admits `n_in % 256 == 0` with the wide bound (`top = 1008`, `narrow = false`) and an
explicit `s_max·127 ≤ i64::MAX` check, which is the `NoQ32` condition `matvec_q8act` requires. A
declined `Q4_K` call, and `k = 1`, take `per_column`; the serial row loop has no `Q4_K` arm. The
carrier is bit-equal to the per-column contract, pinned by
`pooled_q4_k_matches_per_column` (`src/engine/kern/matmat.rs`, shapes `3×512` and `2×1024`,
`k ∈ {2, 8, 33, 64}`); the mutation to turn that test red is any change to the xsum term, the
scale/min bytes or the xsum stride.

`gemm_q4_k` still runs first in `matmat_q8act`; this receipt is the measurement that decides whether
it can be deleted.

## The measurement

Command (release, one binary, both routes, three interleaved passes per cell):

```sh
agent-guard run -- cargo test -j 1 --release --lib --all-features --locked \
  pooled_against_gemm_q4_k -- --ignored --nocapture
```

Payload `Q4_K`, `n_out×n_in = 3584×3584` (14 super-blocks per row, 2016 B/row, 7,225,344 B),
`k ∈ {32, 128, 512}`. Each cell asserts `pooled == gemm` before timing. Exit 0.

| `k` | pooled best / mean ms | gemm best / mean ms | pooled ÷ gemm | pooled GB/s | gemm GB/s |
|---:|---:|---:|---:|---:|---:|
| 32 | 130.972 / 161.213 | 13.665 / 14.828 | **9.58×** | 0.06 | 0.53 |
| 128 | 686.246 / 747.759 | 96.728 / 116.703 | **7.09×** | 0.01 | 0.07 |
| 512 | 3162.320 / 3224.461 | 547.360 / 569.421 | **5.78×** | 0.00 | 0.01 |

The mean/best gap is 10–23% on the pooled arm and 5–21% on gemm, so the ratio is outside the
observed spread at every `k`. The payload is read once per call by both arms; the columns are cheap
against the fold, so the table is compute-bound, not bandwidth-bound. The binding limit is the
`i128` fold: `q4_k_row_kcols_avx2` forms
`S·(d·sc·dot − dmin·m·xsum)` in `i128` per group per column, while `gemm_q4_k` packs eight columns
per `i64` lane with shifts. On this host (`avxvnni = false`) that difference is not recovered by the
AVX2 `vpmaddubsw` plane core.

## Verdict

The carrier is correct and stays, as the refusal/`k = 1` fallback and as the parity target. It is
**not** a throughput replacement: deleting `gemm_q4_k` today would move every 7B `Q4_K` prefill
projection to a loop 5.8–9.6× slower, and no value test would see it. The missing dial is the packed
lane (`Q4KRow`, `q4_k_row_lanes_avx2`, per-column `emin`/`ke`/`spread`, `i64` shift lanes), not the
decode. The entry deletes only after that dial is inside the shared loop and this same command puts
the shared arm inside gemm's spread.

The 7B FFN shape `18,944×256` is also above `MAX_POOLED_WORDS = 2^22` (4.85M words), so the
direct-write task plan (`PBand`/`for_pbands`) must land before that call can route through `pooled`
at all; without it the call falls to the per-column oracle, which is worse than either arm here.

## The parallel `T1` lever

`src/engine/kern/nq.rs`'s scalar `sign_dot!` was vectorized in the same batch (AVX2, `i64` narrow
path, scalar portable and `i128` wide paths unchanged): **4.95×** on the `rank = 1024`,
`inn = 4096` sign dot, three interleaved runs. That is a kernel ratio, not a tok/s claim; the
receipt is `bench/cpu/1794806002-nq-sign-dot.md`.
