# The 0.6B v3 sign-rank pack: 2.52× Q4_K_M perplexity at 0.978 b/w

Criterion: **Q2** — wikitext-2 perplexity within 1.15× the same checkpoint's Q4_K_M (target) and
1.5× (owner's bar). Grade: `measured` for every PPL below; the ratios and the rate–quality
inference are arithmetic and `model`; nothing here is `proved`. Host: Intel Core i5-10210U
(4C/8T), 6.6 GiB, Linux 7.0.0-42-generic, rustc 1.99.0-nightly (`0e29c21d9`, 2026-07-21), release
build (`cargo build --release --locked --example ppl`, 38.33 s). The session's shell sees `nproc`
2; the guard scope ran with `CPUQuota=400%`, a 1674–1881 MiB cap and swap 0. This note measures
one pack; it closes nothing.

## The pack

`APNQPK01` version 3, 28 layers × 7 kinds = **196 sections**, 440,401,920 replaced weights,
53,808,384 factor bytes + 7,088 B of section headers = 53,815,472 B, **0.977441 b/w** (the engine
prints `0.977441`). Every section has `k = 0` salient columns and `res_layers = 0`; there is no
residual and no salient correction. The U and V planes read per token are
Σ rank·(out + in) = **418,381,824 sign terms/token**.

The pack is below the Q1 1.15–1.18 b/w band, so this is a lower-bound data point, not the
production point: the rate under test is below the rate the campaign targets, and a fit at the
production rate would be expected to score no worse. Under that monotone rate–quality assumption
(a `model`, not measured here), 2.524× is the loss the production rate has to beat downward; the
distance to close is 0.926 nats/token, not a rounding.

The image is not 0.978 b/w. The skeleton holds an `F16` token embedding and a separate **`Q8_0`
`output.weight`** (155,582,464 weights each; 311,230,464 weights at 12.4068 b/w in the skeleton).
That head is a dense `Q8_0` reader, not the fitted NQ head in
`bench/cpu/1794810332-nq-head-in-pack.md`.
Skeleton + pack = 536,488,368 B over the checkpoint's 596,049,920 weights = **7.20 b/w**, 1.352×
the Q4_K_M file. Per decode token the NQ arm reads the 53.8 MB pack plus the 165.3 MB `Q8_0` head
plus one embedding row (219.1 MB); Q4_K_M reads its 396.7 MB file. No decode rate is claimed here.

## Protocol

```
target/release/examples/ppl --model /home/lucas/models/qwen3-0.6b-base-f16/Qwen3-0.6B-Base-Q4_K_M.gguf \
  --tokenizer /home/lucas/models/qwen3-0.6b-base-e8/tokenizer.json \
  --data /home/lucas/models/wikitext2/wikitext-2-raw/wiki.test.raw \
  --tokens <2048|8192> --skip 0 --ctx 512 --head-batch 16 --kernel q8act

target/release/examples/ppl --model /home/lucas/models/qwen3-0.6b-base-nq/nq-pack/skeleton-q8head.gguf \
  --pack /tmp/opencode/nq06-v3.nqp --tokenizer ... --data ... \
  --tokens <2048|8192> --skip 0 --ctx 512 --head-batch 16 --kernel <q8act|exact>
```

The `--tokens 2048 --ctx 512` run is four windows (2044 scored positions); the 8192 run is sixteen
(8176). Both arms in a ratio use the identical count, context, skip and head batch, so the token
stream is identical; PPL is deterministic for that stream and one run per arm is enough.

The `ppl.rs` doc comment says the linears run the exact packed product under `--pack`. That is
stale: `--kernel q8act` routes the NanoQuant linears through `NqLinear::project_q8`
(`src/engine/loader/nq.rs:191`, the int8-activation reader) and `exact` through `NqLinear::project`
(the Q32.32 reader). The head follows the mode too: `q8act` uses the fused Q8 reader on the
skeleton's `Q8_0` head, `exact` the reference scalar path on the same head weights.

Clock, `grep MHz /proc/cpuinfo`, 2 samples per run: 3.3 GHz before the 8192-token pair, 3.2 GHz
after Q4, **0.7 GHz** after NQ (its 6.7 tok/s falls from 16.2 at 2044 tokens); the 2044-token runs
sampled 2.9–3.9 GHz. The arms therefore ran at different clocks, but PPL is clock-independent:
every PPL here is computed from exact integer logits at that position, and a rerun at a different
clock returns the same number. The tok/s column is descriptive, not a rate claim.

## Two quantities

The three arms separate the pack's loss from the reader's loss, because the pack and skeleton are
byte-identical across the two NQ arms.

- **Pack quality.** NQ `q8act` / Q4_K_M = 2.524 at 8176 tokens (+0.926 nats/token) and 4.101 at
  2044 (+1.411). Both ratios are outside the 1.15× target and the 1.5× bar.
- **Reader quality.** NQ `q8act` / NQ `exact` = **0.946** at 2044: the int8-activation reader
  scores 5.4% *lower* PPL than the exact reader on the same factors, at 5.2× less wall time
  (126.5 s vs 653.5 s). The reader is not the cause of the 2.5× gap; the pack is. The difference
  is small and bundles the head kernel path (`q8act` fused vs `exact` reference) with the trunk
  reader, so it bounds the reader's quality cost, it does not attribute it.

## The head confound

The NQ skeleton's head is `Q8_0`; the Q4_K_M file has no `output.weight` tensor, so its head is
its tied `Q6_K` token embedding (155,582,464 weights, 6.56 bits/weight against the NQ head's 8.5).
The more precise head is on the NQ arm, so this confound biases toward NQ: it cannot explain a
2.524× deficit. The head change is also part of the shipped configuration — it is the change that
took the 0.6B fixture from 3.44 to 21.42 tok/s (`bench/cpu/1794813322-q8-head-fixture.md`).

## Sample size

The absolute four-window number is not a test-set estimate. Q4_K_M itself moves from 18.119 on the
first four windows to 21.715 on sixteen, a 3.596 PPL (20%) move, so neither absolute value is
comparable to receipts that score the whole test set. The ratios are valid because each pair sees
one identical stream; the 8176-token pair is the primary number and the 2044-token pair is
reported because the `exact` arm was too slow to run at 8192 (653.5 s for 2044 tokens, 3.1 tok/s).

## Context: the 8B v3 pack does not carry down

The 8B v3 pack (two residual layers, 3.130640 b/w) scored 16.295301 against 16.124694 for its
Q4_K_M at ctx 128 over 1008 positions, 1.0106× (`bench/cpu/1794653685-nq8b-residual-ppl.md`).
That pack has 3.2× this pack's rate and a residual the 0.6B pack does not have. The 0.6B pack is
0.978 b/w with neither residual nor salient, and it is 2.524× at more context. The 8B row is a
data point at a different rate, model and host; it is not an expectation for this one.

## What this does not establish

- Context ≥ 2048. The window is 512 tokens; 8176 positions are scored across sixteen windows.
  A 2048-token window is not measured.
- 0-shot accuracy (boolq, piqa, hellaswag, winogrande, arc_easy, arc_challenge). No task harness
  was run.
- The 7B and 8B models. Only the 0.6B v3 pack was run here; the 8B row is a cited receipt from a
  rented host, not a measurement on this machine.
- The head confound. Head types differ by construction (`Q8_0` vs tied `Q6_K`); no head ablation
  was run, so the trunk's own loss is not isolated.
- Fit variants. This pack has no residual layer and no salient columns; a refit with either is a
  different objective and is not measured here.
- Any statement about why the pack scores 2.5×. The exact arm localises the loss to the factors,
  not to the reader, but the fit itself was not inspected.
- rustc and LLVM code generation, the kernel ABI, the Vulkan/SPIR-V path, the GPU and the
  `unsafe` container. No claim here is `proved`.
