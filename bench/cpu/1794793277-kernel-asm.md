# The CPU projection in assembly: what the loop actually executes

Criterion: **T1** (decode) and **T2** (turn latency), partial. Grade: `measured` for the timings,
`model` for the per-row instruction arithmetic; the static counts are exact for the named binary.
The 7B pack and the 30 tok/s target are not covered.

Machine and binary: Intel Core i5-10210U, 4 cores / 8 threads, 15 W, 6.7 GiB RAM, Ubuntu 24.04,
rustc 1.99.0-nightly `0e29c21d9` (2026-07-21). Binary `serve/target/release/nq-serve`, built with
`cargo build --release --locked` from the working tree at `735a7b06` plus the Q5 decode-once change.
The release profile keeps symbols. `tools/asm-hist.py` produced the counts; the full disassembly
is in `/tmp/opencode/asm-*.txt`.

## 2. The inner loop, before and after

Stage 1 (pooled admission) called `q5_0_dot32x4_ptr` once per column per four blocks. That function
measured **139 instructions, 682 bytes**, and decoded the four `Q5_0` blocks inside the call. For
`k = 42`, one row decoded the same 266.7 MB of weights 42 times; the prefill was still compute
bound after the DRAM reads were pooled.

Stage 2 splits the call:

```asm
; q5_0_row_kcols_avx2, one 4-block group
1490e0: call   q5_0_codes4              ; decode 4 blocks, once
...
149100: cmp    %r13,0x28(%rsp)          ; column loop
149105: je     done
14910b: mov    0x20(%rbx),%rdx          ; q.codes
14910f: add    %r12,%rdx
149112: lea    0x60(%rsp),%rdi          ; [i32; 4] return slot
149117: lea    0xa0(%rsp),%rsi          ; decoded codes
14911f: mov    0x44(%rsp),%ecx          ; hoisted vnni flag
149123: call   dot32x4_codes            ; 4 dots, no decode
149128: mov    0x8(%rbx),%r9            ; q.scales
14912c: movslq 0x60(%rsp),%rax
149131: imul   (%r9,%r14,8),%rax
149136: imulq  0x80(%rsp)               ; d[0]
14913e: mov    %rdx,%rcx
149141: mov    %rax,%rsi
...
14919f: mov    %rax,(%r10,%r13,1)      ; i128 low
1491a3: mov    %rdx,0x8(%r10,%r13,1)    ; i128 high
1491a8: add    $0x30,%rbx               ; next column
1491ac: add    $0x10,%r13
```

The decode is 54 instructions once per group; `dot32x4_codes` is 55 instructions per column. The
old per-column path was 139 instructions including decode. For 28 blocks and 42 columns per row,
the stage-2 instruction count in this stage is `7·54 + 7·42·55 = 16,548`, against
`7·42·139 = 40,866` before: **2.47× fewer instructions per row** in the decode-plus-dot stage.

The measured stage-1 to stage-2 change is 2.26 s → 1.84 s to first token (1.23×), not 2.47×,
because the four `i128` scale accumulations after each dot remain (~33 instructions per column)
and the kernel is not purely instruction bound.

## 3. The dot core

`dot32x4_codes` is four blocks in one `reduce4` tree:

```asm
; dot32x4_codes
vpabsb  %ymm?,%ymm0        ; |weight code|
vpsignb %ymm?,%ymm1        ; sign the activation by the weight
vpdpbusd %ymm1,%ymm0,%ymm2 ; u8·i8 dot, 4 products per i32 lane
...
vphaddd %ymm1,%ymm0,%ymm0  ; 3-level horizontal reduction
vextracti128 $0x1,%ymm0,%xmm1
vpaddd  %xmm0,%xmm1,%xmm0
```

On this host `avxvnni = false`, so the AVX2 path executes `vpmaddubsw` + `vpmaddwd`; both paths are
emitted in the same 55-instruction function, selected by one `test`/`je` on the hoisted flag. The
`vpabsb`/`vpsignb` pair is the standard signed×signed-to-u8×i8 conversion; AVX-VNNI has no
signed×signed byte dot, so it does not collapse to one instruction.

## 4. What is removable, and what is not

### 4.1 The feature check

`avxvnni()` loads an `AtomicU8`, compares it with `1` and `2`, and branches. In stage 1 this ran
inside the column loop, once per dot. Stage 2 reads it once per row and passes the bool. The
single-column decoder `q8act_accumulate_row_avx2<Q5_0Decoder>` still has 4 calls and 20 `cmp/test`,
because the trait does not carry the flag; hoisting it is the same change one level up.

### 4.2 The Q5_0 sign expansion

`q5_0_codes4` spends 53 vector instructions per four blocks. Each block is expanded with
`vpsrlw`, `vinserti128`, `vpshufb`, `vpor`, `vpand`, `vpcmpeqb`, `vpor`, `vpxor`, `vpor` (about 8
ops). The Q5_0 code is a 5-bit two's-complement value; the offset form is

```text
u = (qs nibble) | (fifth bit ? 0x10 : 0)     ; c + 16 in [0, 31]
dot(c, x) = dot(u, x) - 16·Σx
```

The offset form needs two ops to build `u` and one `vpsubb` to produce `c` if a signed code is
needed; the dot uses `u` directly with `vpdpbusd` (or `vpmaddubsw`/`vpmaddwd` on AVX2), removing
`vpabsb`/`vpsignb`. That is ~2–4 vector ops per block, on 54% of the demo file's bytes. The cost is
one precomputed `Σx` per activation block per column, reusable across all rows of the call.

### 4.3 Bounds and refusal checks

`quant_act` has 55 `cmp/test` and 64 `jcc`, 16 calls and two `_Unwind_Resume` paths. The checks are
slice bounds (`x[base + lane]`), `Vec::push` capacity, and the final `dequantizes()` pass. The
invariant is local: `take = min(32, x.len() − base)` and `lane < take`, so `base + lane < x.len()`;
`scale ≤ 2^56` makes `scale·127` fit `i64`, so one check per block replaces the per-code
`dequantizes()` pass. Replacing the slice index with a per-block subslice or `get_unchecked` after
the `take` check removes the per-lane compare. This is a proof obligation, not a guess: the bound
is the same one `act_scale` already documents.

`matmat_q8act` is 8,091 bytes, 1,724 instructions, 61 calls and 248 `jcc`. The hot path is a small
part; the per-column `Live`/`Overflow`/`Fallback` state machine and the refusal arms dominate the
function. Outlining the cold arms (`#[cold]`, `#[inline(never)]`) shrinks the hot prologue and
I-cache footprint without changing a word.

The pooled output conversion `i64::try_from(round_shift_32(acc))` is a range check per output. The
admission predicate `fast_family` already proves the call-level `i128` bound; for an admitted call
the check cannot fail. Removing it is safe after that predicate is a theorem (or a debug assertion
plus the existing bound), not before.

### 4.4 What does not collapse

- The four `i128` block accumulations per column are 4 `imul` + 4 `imulq` + 4 `add/adc`; each block
  has its own weight scale and activation scale. A `vpaddq` pair would need a 512-bit accumulator
  for four `i128`s and a carry path; it is not fewer instructions on AVX2.
- `reduce4` is 4 `vphaddd` + extract + add. A `vpshufd`/`vpaddd` tree is one instruction shorter;
  the saving is per four blocks, not per block.
- The `dot32x4_codes` `[i32;4]` return is an sret memory slot: the callee stores 4 `i32`, the caller
  loads 4 `movslq`. Returning `__m128i` in `xmm0` and extracting the lanes removes the store/load
  round trip (about 8 `mov` per column) without changing the arithmetic. `#[inline(always)]` is not
  available with `#[target_feature]` on this toolchain; a non-`target_feature` wrapper or an
  `__m128i` return is the route.

## 5. Cross-ISA status

The row loop, the carrier dial and the `i128` fold are ISA-neutral. The dot core is the only
architecture-specific piece.

| ISA | dp4a-era core | status |
|---|---|---|
| x86-64 | AVX2; AVX-VNNI `vpdpbusd` | implemented; this report |
| ARM | NEON `vdotq_s32` / `vdotq_u32` (ARMv8.2-DotProd) | not implemented; portable scalar is the oracle |
| RISC-V | `V` with `vdot.vv` / `vdot.vx` (Zvdot), or `vwmacc` widening MAC | not implemented; portable scalar is the oracle |
| GPU | Vulkan DP4A `OpSDot`/`OpUDot` (integer dot) | `gpu::simt::Carrier` dial; tested on the Vulkan path |

The portable core is the Lean target; the intrinsics are outside the proof (trust boundary). A
NEON or RVV dot core is a new dial value, not a new row loop.

## 6. The 30 tok/s arithmetic

The host is **dual-channel DDR4-2666** (8 GB soldered model; Lenovo PSREF), spec peak
`2 × 2666 MT/s × 8 B = 42.656 GB/s`. A four-thread sequential read measures **27.97 GB/s** under
the `performance` platform profile and **7.78 GB/s** under `power-saver`; the timings in Sections
2–3 were taken in `power-saver` at 0.6–0.9 GHz. The full measurement is
`bench/cpu/1794799742-decode-ceiling.md`.

The 7B pack at 1.174 b/w is 957,615,232 B, but the served per-token read also includes the untied
Q6_K `output.weight` (544,997,376 weights = 447,068,160 B), which `Engine::lm_head` reads every
token: **1,404,683,392 B/token**. At 30 tok/s that is **42.14 GB/s**, 98.8% of spec peak before KV.
The measured 28.0 GB/s gives **19.9 tok/s**. The 0.5B per-token read is 397.8 MB (the token
embedding is a lookup; its Q8_0 output head is read), so 10.2 tok/s was 4.07 GB/s and the
performance-profile 40.3 tok/s is 16.03 GB/s.

The 30 tok/s target therefore needs the LM head inside the 1.17 b/w compression budget and a
lower-b/w pack, not only a smaller per-layer pack. The 200k 24 tok/s bar additionally needs a
context method that reads at most ~372 MB/token at peak, because the full 869 MB C1 plan plus the
head is 2.27 GB/token and 54.6 GB/s. These are the open Q1/T1 problems; the instruction ceiling in
Section 4.4 is the other half (about 1 instruction/weight caps 6.525G weights at 2.4–4.9 tok/s at
4 GHz).

## 7. Reproduce

```sh
cd serve && cargo build --release --locked
cd .. && python3 tools/asm-hist.py serve/target/release/nq-serve \
    q5_0_row_kcols_avx2 dot32x4_codes q5_0_codes4 quant_act matmat_q8act
objdump -d --demangle --no-show-raw-insn \
    --start-address=0x148e50 --stop-address=0x1492c9 serve/target/release/nq-serve
```

Addresses move with the build; `nm -S -C` gives the current range.
